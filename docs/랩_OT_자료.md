# 랩 OT 자료 — 스테이블코인 디페그 조기경보 프로젝트

> **대상**: 이번 학기 랩 신규 및 전체 멤버
> **목적**: 랩 정체성, 프로젝트 개요, 역할 분담, 학기 운영 방식 공유
> **사전 자료**: 『스테이블코인 배경지식 온보딩 문서』 (OT 전 필독)

---

## 1. 우리 랩은 어떤 랩인가

### 1-1. 한 줄 정의

- 우리 랩 = **산업 도메인의 운영 의사결정을 자동화하는 시스템을 만드는 랩**임 (랩 이름은 추후 확정 예정)

### 1-2. 차별화 포인트: 탐지가 아니라 대응까지

- 이상 탐지·예측 모델은 IE, 데이터사이언스, 통계학과도 만듦
- 우리 랩의 영역은 그 다음 단계임 — **예측을 의사결정과 실행으로 연결하는 시스템 설계**
- 화재 비유로 정리하면:
  - 화재 감지기 = 이상 탐지 (누구나 만드는 것)
  - 스프링클러 + 대피 방송 + 소방서 자동 신고 = 대응 자동화 (우리 랩이 만드는 것)
- 핵심 역량 세 가지: 의사결정 자동화, 공급망·도메인 맥락 통합, 역할 기반 정보 설계(같은 경보라도 받는 사람마다 다른 정보를 전달하는 것)

### 1-3. 랩의 프로젝트 계보

- **YieldWatch** (반도체): 수율 이상 탐지 → 영향 스코어링 → 역할별 알림
- **AeroMind / 지연 전파 플랫폼** (항공): 정비 우선순위, 지연 전파 예측
- **이번 학기 (핀테크)**: 스테이블코인 디페그 조기경보 + 대응 자동화 — 위 아키텍처 패턴의 세 번째 도메인 이식임
- 도메인은 바뀌어도 시스템 설계의 본질은 동일함 — 감시 대상이 수율이든, 항공기든, 준비금이든 "탐지 → 영향평가 → 역할별 대응"의 구조는 같은 것

## 2. 이번 학기 프로젝트: 왜 지금 스테이블코인인가

### 2-1. 프로젝트 한 줄 요약

- 스테이블코인의 디페그(1달러 고정 붕괴) 리스크를 온체인 + 오프체인 데이터로 조기 탐지하고, 이해관계자 역할별로 다른 대응을 자동 실행하는 시스템을 만드는 것

### 2-2. 타이밍: 규제의 골든타임

- 미국은 2025년 GENIUS Act로 스테이블코인을 법제화했고, 홍콩은 2026년 아시아 최초 라이선스를 발급함
- 한국은 원화 스테이블코인을 허용하는 디지털자산기본법 입법을 하반기 추진 중 — **이번 학기가 정확히 제도화 국면과 겹치는 것**
- 비유: 자동차는 이미 도로를 달리는데 도로교통법이 이제 만들어지는 상황 — 법이 확정되면 리스크 감시 시스템은 선택이 아닌 의무가 됨

### 2-3. 산업 맥락: 반도체와 핀테크의 융합

- 엔비디아가 월가 6대 금융사와 GPU·데이터센터를 담보로 한 5,000억 달러 규모 금융 플랫폼을 추진 중 — "뱅크 오브 엔비디아"
- GPU 담보 대출의 리스크 = "담보 가치가 유지되는가"의 감시 문제이고, 스테이블코인의 리스크 = "준비금 가치가 유지되는가"의 감시 문제 — **구조적으로 같은 문제**임
- 우리 랩의 두 도메인(반도체, 핀테크)이 실제 산업에서 융합되고 있다는 증거이자, 본 프로젝트에서 검증한 아키텍처가 향후 실물자산(RWA) 리스크 감시로 확장 가능한 근거임

### 2-4. 최종 데모의 목표 장면

- 실시간 온체인 + 공시 데이터 → 리스크 스코어 산출 → 임계값 초과 시 역할별 대응 자동 실행
- 백테스트 헤드라인: **"우리 시스템이었다면 2023년 USDC 디페그를 몇 시간 전에 경보했는가"**

## 3. 레퍼런스 아키텍처: ThreatWatch AI

### 3-1. ThreatWatch가 무엇인가

- 랩장이 완성한 AI 기반 보안 알림 트리아지 플랫폼 — 이번 학기 우리의 **교재이자 설계 원형**임
- 완성된 범위: 서버리스 파이프라인(API Gateway → SQS → Lambda → DynamoDB/S3/SNS), 전체 인프라 코드화(Terraform), CI/CD(GitHub Actions), HMAC 인증, 사람 승인 워크플로우(HITL)까지 전부 가동 중
- 우리 프로젝트와의 관계: **ThreatWatch = 교재, 디페그 프로젝트 = 실습장**
  - ThreatWatch: 보안 알림 탐지 → 위험 평가 → P1이면 사람 승인 대기 → 승인/반려/만료 처리
  - 디페그 프로젝트: 디페그 시그널 탐지 → 리스크 스코어 → 임계값 초과 시 대응 승인 대기 → 역할별 대응 실행
  - 구조가 1:1로 대응하므로, ThreatWatch를 읽으면 우리가 만들 시스템의 완성형을 미리 보는 것

### 3-2. 특히 주목할 설계 사상 (전원 공통)

- **멱등성**: 같은 알림이 두 번 와도 중복 처리되지 않는 조건부 쓰기 설계
- **실패의 분류**: 재시도해도 똑같이 실패할 입력은 즉시 버리고, 일시적 오류만 재시도하는 것 — 예외 타입 설계가 시스템 신뢰성을 좌우함
- **fallback 금지 원칙**: 평가 실패 시 대충 낮은 등급으로 저장하는 것보다 실패를 드러내는 게 나음 — P1 사고를 P2로 기록하는 시스템은 없느니만 못한 것
- **타임아웃도 하나의 결과**: 아무도 응답하지 않는 것 자체가 대응이 필요한 상황임 — 침묵을 삼키지 않고 기록·재알림하는 설계

## 4. 협업 모델: 각자의 역할 경계

### 4-1. 대원칙

- **설계와 코드는 학생, 실행과 배포는 랩장**
- 학생은 AWS 계정 없이, 클라우드 경험 없이 첫 주부터 기여 가능한 구조임
- AWS 계정·인프라·시크릿·배포는 전부 랩장이 운영 — 학생 코드는 랩장이 Lambda로 감싸 클라우드에 탑재하는 것

### 4-2. 학생 작업 환경

- 순수 Python + 로컬 환경 + mock 데이터가 학기 전반의 작업 방식임
- **단 하나의 규칙: 모든 모듈은 순수 함수로, I/O는 바깥에서 주입할 것**
  - 이 규칙만 지키면 로컬에서 돌던 코드가 며칠 만에 클라우드에 탑재됨 (ThreatWatch에서 검증된 방식)
- 팀 간 연결은 **데이터 계약(JSON 스키마)**으로만 이루어짐 — 옆 팀이 늦어져도 mock 데이터로 내 작업은 계속 진행 가능한 구조

### 4-3. 협업 파이프라인

- 저장소 브랜치에서 작업 → PR 생성 → CI 자동 검사 → 랩장 리뷰·머지
- PR에 인프라 변경 계획(terraform plan)이 자동 코멘트로 달림 — **클라우드를 직접 만지지 않아도, 내 코드가 클라우드에서 무엇을 일으키는지 읽는 훈련**이 되는 것
- 커밋·PR 규약은 별도 CONTRIBUTING 문서로 배포 예정

## 5. 역할 분담

### 5-0. 전체 구조

| 역할 | 메인 과제 |
|---|---|
| 1. 온체인 데이터 수집 | 시장 데이터 수집이 메인 과제 |
| 2. 오프체인 인텔리전스 | 공시 문서(PDF) 구조화가 메인 과제 |
| 3. 리스크 엔진 + 백테스트 | 리스크 스코어 산출과 검증이 메인 과제 |
| 4. 대응 설계 | 경보 이후의 대응 체계 설계가 메인 과제 |

- 데이터 흐름: 1·2번이 데이터를 만들고 → 3번이 점수를 매기고 → 4번의 설계대로 대응이 나가는 구조임

### 역할 1. 온체인 데이터 수집 (1명)

- **메인 과제**: 거래소·블록체인에서 가격, 유동성 데이터를 자동 수집하는 Python 수집기를 만드는 것
- **첫 목표**: 과거 사고 두 건(2022 테라, 2023 USDC) 주간의 데이터 확보 — 백테스트의 원료임
- **적합**: API 연동에 흥미 있는 사람. 블록체인 지식은 하면서 배우면 됨
- **세미나 파트**: 데이터 인입 경로

### 역할 2. 오프체인 인텔리전스 (1명)

- **메인 과제**: 발행사의 준비금 공시 보고서(PDF)를 구조화된 데이터로 변환하는 파이프라인을 만드는 것
- **첫 목표**: USDT/USDC 최근 3개월치 보고서의 구조화 변환
- **적합**: 문서를 꼼꼼히 읽고 정리하는 성격. 회계 지식 불필요
- **세미나 파트**: 저장·분석 계층

### 역할 3. 리스크 엔진 + 백테스트 (1~2명)

- **메인 과제**: 역할 1·2의 데이터를 종합해 디페그 리스크 스코어를 계산하는 엔진을 만들고, 과거 데이터로 성능을 검증하는 것
- **첫 목표**: "USDC 하락을 몇 시간 전에 경보 가능했는가" 백테스트 — 최종 발표의 헤드라인 수치임
- **적합**: 팀에서 통계·수학이 가장 편한 사람 (pandas, 시계열 분석)
- **세미나 파트**: 처리 엔진

### 역할 4. 대응 설계 (1명)

- **메인 과제**: 경보 발생 후 이해관계자별(자금/준법/일반 사용자)로 누가 무엇을 승인하고 어떤 안내를 받는지 정의하는 대응 매트릭스와 순서도를 설계하는 것
- **첫 목표**: ThreatWatch의 승인 워크플로우를 읽고 디페그 버전 상태 전이 다이어그램 초안 작성
- **적합**: 코딩 부담이 가장 적은 대신 도메인 이해·분석력이 가장 중요한 자리
- **세미나 파트**: 인증·승인 워크플로우

### 공통 사항

- 시스템 구조 공부(아키텍처 리딩)는 전원이 함께함 — 각자 세미나 파트가 자기 리딩 범위임
- 문서화 전담자는 없음 — 자기가 만든 모듈은 자기가 문서화하는 것이 원칙임
- 발표 시 AWS 심화 내용은 랩장이 보충함

## 6. 학기 로드맵

| 주차 | 내용 |
|---|---|
| 1~2주 | **온보딩**: 스테이블코인 문서 세미나, UST·USDC 사례 타임라인 분석, ThreatWatch 로테이션 세미나(4파트), 데이터 계약(스키마) 확정 리뷰 미팅 |
| 3~7주 | **병렬 구현**: 전원 mock 기반 로컬 작업, 주간 스탠드업(계약 변경사항만 공유), 랩장 PR 리뷰 |
| 8주 | **mock 관통 데모**: 역할 1·2 출력 → 역할 3 스코어 → 역할 4 대응 매트릭스 → 3가지 결과 중 하나로 종결까지, 전부 로컬에서 관통 |
| 9주~ | **클라우드 탑재**: 랩장이 학생 코드를 Lambda로 감싸 실제 인프라에 배포, 실데이터 연결. 격주 AWS 세미나 시작 |
| 학기말 | **최종 데모**: 실시간 온체인 데이터 라이브 시연 + 백테스트 결과 발표 |

- 8주차 관통 데모는 미룰 수 없는 고정 마일스톤임 — 통합을 학기말로 미루는 프로젝트는 반드시 학기말에 무너지는 것
- 9주차 이후 자기 모듈이 클라우드에서 도는 것을 처음 보게 됨 — 그 시점부터 AWS 개념 세미나를 병행하는 것

## 7. 운영 교훈 세션 (OT 특강, 랩장 진행)

실제 시스템을 운영하며 겪은 실수 세 가지 — 이번 학기 여러분이 반드시 마주칠 실수의 예방주사임

- **초록불을 의심할 것**: CI에서 실패한 검사가 파이프 처리 실수로 성공처럼 표시된 사건 — 두 개의 결함이 서로를 가려서 원인 추적이 늦어진 사례. 테스트가 통과했다는 것과 시스템이 옳다는 것은 다른 명제임
- **최적화는 이유를 알고 나서**: 배포 패키지 크기를 줄이려고 메타데이터 폴더를 삭제했다가 런타임에서 라이브러리가 깨진 사건 — 왜 존재하는지 모르는 파일을 지우지 말 것
- **버전은 고정할 것**: 의존성 버전을 범위(>=)로 열어두면 설치 시점마다 다른 버전이 깔려 버그가 늦게, 랜덤하게 발현됨 — 우리 저장소의 requirements.txt는 처음부터 정확한 버전(==)으로 고정하는 것

- 질문은 랩 채널에 자유롭게 남길 것 — 질문이 문서를 개선하고, 개선된 문서가 다음 기수의 온보딩이 되는 것
